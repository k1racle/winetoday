# Дизайн-документ: новая структура аккаунта и CMS

> Документ описывает предлагаемую перестройку текущего `/account` в более логичную систему с отдельным пользовательским кабинетом и отдельной CMS-оболочкой в стиле WordPress.
> Основа документа: текущая структура страниц `web/pages/account/*`, табы `AccountTabs`, `AdminTabs`, `ProjectTabs` и фактические сценарии редакции/администрирования.

---

## 1. Задача

Сейчас интерфейс перегружен и смешивает несколько разных контуров:

- личный кабинет пользователя;
- редакторскую CMS;
- системную админку;
- управление спецпроектами.

Из-за этого:

- `/account` не имеет одной понятной роли;
- навигация размазана по нескольким горизонтальным таб-барам;
- похожие по смыслу задачи разнесены по разным разделам;
- у сложных разделов нет собственной структуры;
- спецпроекты живут как вложенный остров внутри общего кабинета.

Цель: собрать понятную IA и интерфейс, где пользователь всегда понимает:

- где он находится;
- чем этот раздел отличается от соседнего;
- какие действия доступны прямо здесь;
- как быстро перейти к материалам, страницам, настройкам и спецпроектам.

---

## 2. Что есть сейчас

### 2.1 Текущие контуры

- `/account` — профиль, подписки, лайки, комментарии, редактор, главная, спецпроекты.
- `/account/admin/*` — пользователи, авторы, материалы, медиа, комментарии, рубрики, теги, соцсети, подписчики, страницы, UTM, настройки.
- `/account/projects/*` — спецпроекты.

### 2.2 Основные проблемы

1. Один URL-контур решает слишком разные задачи.
2. Личный кабинет и CMS визуально почти не разделены.
3. Основная навигация построена через верхние табы, хотя разделов уже слишком много.
4. У разделов нет постоянного левого меню и устойчивой структуры.
5. Страница спецпроекта `Виноделы России` стала слишком тяжёлой: доступ, витрина, сущности и редакторы живут в одном месте.
6. Заголовок `Личный кабинет` повторяется даже там, где пользователь находится уже в редакционной CMS.

---

## 3. Принципы новой структуры

### 3.1 Жёсткое разделение контуров

Нужно развести:

- `Аккаунт` — личные действия пользователя;
- `CMS` — редакционные и административные действия;
- `Спецпроекты` — отдельный большой контур внутри CMS.

### 3.2 Навигация как в WordPress

Основа интерфейса:

- постоянный левый sidebar;
- верхняя служебная панель;
- breadcrumb;
- чёткий заголовок страницы;
- primary action справа;
- внутренние вкладки только как локальная навигация внутри конкретного раздела.

### 3.3 Один экран — одна задача

Нельзя держать на одной странице одновременно:

- список сущностей;
- системные настройки;
- публикацию;
- редактор контента;
- модальные редакторы сложных сущностей.

---

## 4. Целевая модель разделов

## 4.1 Аккаунт

`Аккаунт` остаётся обычным пользовательским кабинетом.

Содержимое:

- Профиль
- Подписки
- Лайки
- Комментарии

Никакой CMS-логики здесь быть не должно.

### 4.2 CMS

`CMS` — отдельная оболочка для авторов, редакторов и админов.

Варианты URL:

- предпочтительно `/cms/*`
- допустимо `/account/cms/*`

Рекомендация: использовать `/cms/*`, чтобы визуально и логически отделить CMS от обычного аккаунта.

### 4.3 Спецпроекты

`Спецпроекты` — отдельный большой раздел внутри CMS.

Не вкладка личного кабинета, а самостоятельный модуль:

- `/cms/projects`
- `/cms/projects/winemakers/*`

---

## 5. Роли и доступ

### 5.1 Member

Видит только:

- Аккаунт
- Профиль
- Подписки
- Лайки
- Комментарии

### 5.2 Author

Видит:

- Аккаунт
- CMS
- свои материалы
- создание материала

Не видит:

- системные настройки;
- пользователей;
- спецпроекты;
- глобальные настройки сайта.

### 5.3 Editor

Видит:

- материалы;
- страницы;
- медиа;
- комментарии;
- авторов;
- главную сайта.

Опционально:

- часть спецпроектов, если это нужно редакционно.

### 5.4 Admin

Видит всё:

- CMS полностью;
- спецпроекты;
- пользователей;
- настройки;
- маркетинг;
- системные разделы.

```text
+--------------------------------------------------------------+

+--------------------------------------------------------------+
```

### 7.2 CMS shell

```text
+----------------------------------------------------------------------------------+
| CMS Bar: логотип | поиск | быстрые действия | профиль | выйти                    |
+---------------------------+------------------------------------------------------+
| Sidebar                   | Breadcrumb: CMS / Материалы / Все материалы         |
|                           | Title: Материалы                         [+ Добавить]|
| - Дашборд                 +------------------------------------------------------+

| - Комментарии             |                                                      |
| - Рубрики и теги          |                                                      |
| - Авторы                  |                                                      |

| - Настройки               |                                                      |

```

### 7.3 Список сущностей

Для всех списков нужен единый шаблон:

- breadcrumb;
- title;
- primary action;
- строка поиска;
- фильтры;
- статусные счётчики;
- таблица или grid;
- пагинация.

Применить к:

- материалам;
- страницам;
- авторам;
- пользователям;
- сущностям спецпроекта.

### 7.4 Экран редактирования

```text
| Breadcrumb: CMS / Материалы / Редактирование                                     |
```

## 9. Дашборд CMS

Первый экран CMS должен быть не «Пользователи», а нормальный дашборд.

Содержимое:

- количество материалов по статусам;
- последние черновики;
- материалы на проверке;
- последние комментарии;
- быстрые переходы;
- состояние спецпроектов;
- последние действия редакции.

Пример:

```text
+--------------------------------------------------------------+
| Дашборд                                           [+ Материал]|
+--------------------------------------------------------------+
| 24 Черновика | 8 На проверке | 312 Опубликовано | 5 Жалоб    |
+--------------------------------------------------------------+
| Последние материалы     | Последние комментарии             |
| Быстрые действия        | Спецпроекты                       |
+--------------------------------------------------------------+
```

---

## 10. Что переносим без глубокого рефакторинга

На первом этапе можно сохранить текущую логику страниц и API, но посадить их в новую оболочку.

Без переписывания бизнес-логики:

- `admin/content.vue` становится экраном `CMS / Материалы`;
- `admin/media.vue` становится экраном `CMS / Медиа`;
- `admin/settings.vue` становится экраном `CMS / Настройки`;
- `account/homepage.vue` переезжает в `CMS / Главная сайта`;
- `projects/winemakers.vue` режется минимум на 3 экрана:
  - обзор;
  - главная проекта;
  - сущности.

## 11. Визуальные правила

### 11.1 Общий тон

- интерфейс строгий, редакционный;
- меньше декоративных блоков;
- больше плотности, структуры и иерархии;
- основной акцент на скорости навигации.

### 11.2 Что важно сохранить

- текущую цветовую тему сайта;
- текущую типографику, если она уже согласована;
- единый стиль кнопок и форм;
- общую медиа-библиотеку и редакторский стек.

### 11.3 Что важно изменить

- отказаться от табов как главной навигации;
- ввести устойчивый sidebar;
- ввести единый шаблон списков;
- ввести единый шаблон редактирования;
- перестать дублировать заголовок `Личный кабинет` внутри CMS.

## 13. Этапы внедрения

### Этап 1. Новая оболочка

- создать `cms` layout;
- сделать левое меню;
- сделать header CMS;
- сделать breadcrumb и page header;
- определить ролевую видимость пунктов меню.

### Этап 2. Перенос существующих страниц

- перенести материалы, медиа, настройки, комментарии, страницы;
- убрать зависимость от старых tab-компонентов;
- оставить текущие формы, если они уже рабочие.

### Этап 3. Рефактор спецпроектов

- вынести `Виноделы России` в отдельное дерево экранов;
- разрезать огромный экран на обзор, списки и редакторы;
- перевести редакторы сущностей на отдельные страницы.

### Этап 4. Полировка

- быстрые действия;
- последние действия;
- bulk actions;
- сохранённые фильтры;
- улучшенный поиск.

---

## 14. Рекомендуемое решение

Рекомендуется принять следующую модель как целевую:

1. `/account` оставить только как личный кабинет.
2. Создать отдельный контур `/cms`.
3. Внутри `/cms` сделать постоянный левый sidebar.
4. `Спецпроекты` вынести в самостоятельный большой раздел.
5. `Виноделы России` разложить на обзор, публикацию, главную и отдельные списки сущностей.
6. Тяжёлые редакторы переводить на отдельные страницы, а не держать в одной гигантской форме.

Это даст:

- более понятную архитектуру;
- лучшую масштабируемость;
- интерфейс ближе к привычной CMS-логике;
- меньше хаоса при дальнейшем росте разделов.

---

## 15. Следующий практический шаг

Если брать этот документ как основу реализации, следующий шаг должен быть таким:

1. Утвердить IA и названия разделов.
2. Сделать `cms` layout и sidebar.
3. Перенести в него существующие страницы без смены API.
4. После этого отдельно резать и упорядочивать спецпроекты.
